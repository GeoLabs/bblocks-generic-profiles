
# Activity type (Schema)

`generic-profiles.activity-type` *v0.1*

The shape every activity type of this register shares: the meaning of one operation, as an acttype:ActivityType item of the Activity Type Register's item class, held in gp:register. One per operation, distinct from the Implementation Profile that points to it with activityType.

[*Status*](http://www.opengis.net/def/status): Under development

## Description

Activity type -- the shape every activity type of this register shares.

## What an activity type holds here

The meaning of one operation: its name, its definition, the standards and literature that define
it, and its illustrations (decision D3, 2026-11-05). It holds no input, output, format, tool or
deployment. Each one is a register item of this register (`gp:register`), typed
`acttype:ActivityType` and of the Activity Type Register's item class, and an OWL class:

```turtle
gpat:intersects a acttype:ActivityType , owl:Class ;
    rdfs:subClassOf geoproc:GeoprocessingActivityType ;
    rim:inRegister gp:register ;
    rim:itemClass acttype:activityTypeItemClass ;
    acttype:usedEntityType geo:Geometry ;
    acttype:associatedAgentType prov:SoftwareAgent .
```

This is the pattern of `docs/questions-for-rim-atr-maintainers.md` ("What we plan to do"). The
Implementation Profile of the operation is a different item, of a different item class, and points
here with `activityType` (`gp:activityType`, a sub-property of `rim:relatedItem`):
`rim:RegisterItemShape` allows one item class per item, so a profile cannot be its own activity type
(`docs/implementation-profile-vs-activity-type.md`).

There are 36 activity types, one per operation (decision D3). The 37 Implementation Profiles point to them;
two point to the same one, `radiometric-index` (decision C4 of 2026-11-10). The items are generated by
`scripts/activity_types.py` from `scripts/activity-types.yaml`; the item class IRI is written from one
constant of that script, because the upstream branch `model-tweaks` renames it.

## Geoprocessing: all 36

All 36 activity types are sub-classes of `geoproc:GeoprocessingActivityType` (decision of
2026-11-09). The geoproc shapes require at least one used or generated entity type that is, or
specialises, a GeoSPARQL 1.1 spatial class (`geo:SpatialObject`, `geo:Feature`, `geo:Geometry`,
`geo:SpatialObjectCollection`, `geo:FeatureCollection`, `geo:GeometryCollection`). The class is
chosen directly per kind of role, not derived from the data types of `bblocks-data-types`:

| Kind of role (data type) | Entity type | Why |
|---|---|---|
| `geometry`, `surface`, `point` | `geo:Geometry` | a geometry, as in the tested pattern |
| `bounding-box` | `geo:Geometry` | GeoSPARQL 1.1 (OGC 22-047r1, 8.4.3) gives `geo:hasBoundingBox` the range `geo:Geometry` ; not used today: `raster-crop` and `band-retrieval`, the operations with a bounding box, declare one used entity type (the ATR JSON schema allows one), `geo:Feature` for their raster or product |
| `raster`, `raster-single-band`, `elevation-model`, `binary-mask` | `geo:Feature` | a coverage described as a feature, the reading `geoproc:GeoprocessingActivityType` states; the ATR NDVI example makes its rasters sub-classes of `geo:Feature` |
| `point-cloud` | `geo:Feature` | a point cloud dataset, described as a feature like a coverage |
| `feature-collection` | `geo:FeatureCollection` | a collection of features |
| `eo-product` | `geo:Feature` | a product, described by a record with a footprint (band-retrieval, product-selection) |
| number, boolean, expression, CRS, format identifier, radiometric index, band identifier, grid resolution, time interval, collection identifier, colour map | none | not spatial data |
| `rendered-image` | none | a picture, not georeferenced in general: raster-rendering declares a used entity type only |

How a data type of `bblocks-data-types` becomes an entity type (a class bridge) is question 5 to the
maintainers and stays open (decision D8).

## What is not settled here

Decision D8 is open. Nothing here says how a run of one of these operations is typed (`rdf:type` or
`prov:type`), whether `acttype:ActivityType` specialises `prov:Activity`, or how a tier-4 process type
of `bblocks-process-profiles` relates to these items.

## Validation

`shapes.shacl` adds, for every activity type: `gp:register`, a `skos:prefLabel`, a `skos:definition`,
the `owl:Class` type and a proposed addition. The Activity Type Register's shapes and
`rim:RegisterItemShape` apply through `dependsOn`. `tests/` holds one failing fixture per constraint
and a control.

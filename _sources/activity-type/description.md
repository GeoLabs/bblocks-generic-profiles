Activity type -- the shape every activity type of this register shares.

## What an activity type holds here

The meaning of one operation: its name, its definition, the standards and literature that define
it, and its illustrations (decision D3, 2026-11-05). It holds no input, output, format, tool or
deployment. Each one is a register item of this register (`gp:register`), typed
`acttype:ActivityType` and of the Activity Type Register's item class, and an OWL class:

```turtle
gpat:intersects a acttype:ActivityType , owl:Class ;
    rdfs:subClassOf geoproc:GeoprocessingActivityType ;
    rim:inRegister gp:register ;
    rim:itemClass acttype:activityTypeItemClass ;
    acttype:usedEntityType geo:Geometry ;
    acttype:associatedAgentType prov:SoftwareAgent .
```

This is the pattern of `docs/questions-for-rim-atr-maintainers.md` ("What we plan to do"). The
Implementation Profile of the operation is a different item, of a different item class, and points
here with `activityType` (`gp:activityType`, a sub-property of `rim:relatedItem`):
`rim:RegisterItemShape` allows one item class per item, so a profile cannot be its own activity type
(`docs/implementation-profile-vs-activity-type.md`).

There are 35 published activity types, one per operation (decision D3), and 16 families that group
them (below). The 37 Implementation Profiles point to the operations: two point to `radiometric-index`
(decision C4 of 2026-11-10), two to `raster-band-math` (decision of 2026-11-19). The items are generated by
`scripts/activity_types.py` from `scripts/activity-types.yaml`; the item class IRI is written from one
constant of that script, because the upstream branch `model-tweaks` renames it.

## Families (decision of 2026-11-19)

The operations are grouped by **meaning** into 16 families, abstract activity types proposed by
GeoLabs (no source defines these groupings). A family is a sub-class of
`geoproc:GeoprocessingActivityType`, and each operation is a sub-class of its family. The Generic
Profiles group the same operations by **signature** (WPS 2.0.2 §7.5), another axis: a family may
coincide with a Generic Profile (`spatial-relation-test` and `binary-spatial-predicate`) or cut across
several (`band-algebra` holds `raster-band-math` and `radiometric-index`; `extent-computation` holds a
vector and a raster operation; `coverage-subsetting` holds `raster-crop` and `band-retrieval`, under two
Process Concepts). No Implementation Profile points to a family: the schema of the Implementation
Profiles lists the published operations only.

| Family | Operations |
|---|---|
| spatial-relation-test | contains, crosses, disjoint, equals, intersects, touches, within |
| set-operation | union, intersection, difference, symdifference |
| geometry-construction | buffer, centroid, convex-hull |
| extent-computation | geometry-extent, raster-extent |
| terrain-derivative | slope, terrain-ruggedness-index, topographic-position-index, analytical-hillshading |
| band-algebra | raster-band-math, radiometric-index |
| raster-regridding | raster-reprojection, raster-resampling |
| coverage-subsetting | raster-crop, band-retrieval |
| spatial-model-conversion | point-cloud-to-grid, point-cloud-to-shapes |
| geometry-measure | area |
| geometry-property-test | is-simple |
| raster-classification | otsu-thresholding |
| point-cloud-filtering | point-cloud-thinning |
| encoding-conversion | raster-format-conversion |
| portrayal | raster-rendering |
| catalogue-search | product-selection |

A family with one member waits for the other operations of its kind. A family's entity types are
those common to its members, one value per property (ATR JSON schema); `extent-computation` uses
`geo:SpatialObject`, the parent of `geo:Geometry` and `geo:Feature`. Moving each operation under its
family is a change of parent class, recorded by a substantive amendment (`family-2026-11-19`).

When an operation's example is validated alone, its family's own `rdfs:subClassOf` is not in the
graph. `families.ttl`, a data resource of this block generated by the script, states it (untyped), so
that `geoproc:GeoprocessingActivityTypesShape` reaches the operation through its family
(`tests/family-member-without-spatial-entity-fail.ttl`).

`raster-band-math-multiband` is withdrawn (2026-11-19): the same operation as `raster-band-math`, the
number of output bands being a matter of signature, already enforced by each Implementation Profile's
output `dataType`. It stays, unpublished, with an `unpublish` action classified substantive and
`dct:isReplacedBy` towards `raster-band-math`, as the data-types register did for its `string-*` items
(`rim:supersededBy` would require `raster-band-math` to be typed `rim:RegisterItem` in the graph of the
withdrawn item, which is validated alone).

## Geoprocessing

All activity types, the families and the operations under them, are sub-classes of
`geoproc:GeoprocessingActivityType` (decision of 2026-11-09), whose definition is an activity that
uses or generates spatial data. The geoproc shapes require at least one used or generated entity type that is, or
specialises, a GeoSPARQL 1.1 spatial class (`geo:SpatialObject`, `geo:Feature`, `geo:Geometry`,
`geo:SpatialObjectCollection`, `geo:FeatureCollection`, `geo:GeometryCollection`). The class is
chosen directly per kind of role, not derived from the data types of `bblocks-data-types`:

| Kind of role (data type) | Entity type | Why |
|---|---|---|
| `geometry`, `surface`, `point` | `geo:Geometry` | a geometry, as in the tested pattern |
| `bounding-box` | `geo:Geometry` | GeoSPARQL 1.1 (OGC 22-047r1, 8.4.3) gives `geo:hasBoundingBox` the range `geo:Geometry` ; not used today: `raster-crop` and `band-retrieval`, the operations with a bounding box, declare one used entity type (the ATR JSON schema allows one), `geo:Feature` for their raster or product |
| `raster`, `raster-single-band`, `elevation-model`, `binary-mask` | `geo:Feature` | a coverage described as a feature, the reading `geoproc:GeoprocessingActivityType` states; the ATR NDVI example makes its rasters sub-classes of `geo:Feature` |
| `point-cloud` | `geo:Feature` | a point cloud dataset, described as a feature like a coverage |
| `feature-collection` | `geo:FeatureCollection` | a collection of features |
| `eo-product` | `geo:Feature` | a product, described by a record with a footprint (band-retrieval, product-selection) |
| number, boolean, expression, CRS, format identifier, radiometric index, band identifier, grid resolution, time interval, collection identifier, colour map | none | not spatial data |
| `rendered-image` | none | a picture, not georeferenced in general: raster-rendering declares a used entity type only |

How a data type of `bblocks-data-types` becomes an entity type (a class bridge) is question 5 to the
maintainers and stays open (decision D8).

## What is not settled here

Decision D8 is open. Nothing here says how a run of one of these operations is typed (`rdf:type` or
`prov:type`), whether `acttype:ActivityType` specialises `prov:Activity`, or how a tier-4 process type
of `bblocks-process-profiles` relates to these items.

## Validation

`shapes.shacl` adds, for every activity type: `gp:register`, a `skos:prefLabel`, a `skos:definition`,
the `owl:Class` type and a proposed addition. The Activity Type Register's shapes and
`rim:RegisterItemShape` apply through `dependsOn`. `tests/` holds one failing fixture per constraint
and a control.
